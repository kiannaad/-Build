# 2026-11-25 记忆恢复与衰减监控

## 时间

2026-11-25 23:15–23:35（Asia/Shanghai）

## 原因

1. 拒绝/遗忘是软删除，但没有恢复入口，误操作只能改库。
2. 退化任务只能手动跑；心跳里至少应该报告「哪些记忆快过期」，但不该擅自归档。

## 改动

1. `db.restore_memory(memory_id, reason)`：`deleted` / `archived` → `candidate`，清空 `archived_at`，写 `restore` 审计；状态不符报错。
2. MCP 新增 `memory_restore`。
3. `auto_tick.tick_once()` 增加 `decay_job.archive_stale(dry_run=True)`：心跳只统计 `stale` 数量，**不写归档**；返回值多一个 `stale` 字段。
4. 测试：恢复流程（拒绝→恢复→候选列表）、心跳含 stale 统计。

## 影响面

- 工具变为 15 个。
- 恢复走审核队列（candidate），不会直接变 active。
- 归档仍需显式 `memory_decay(dry_run=false)`；自动心跳不动数据。

## 验证证据

```text

```

真实链路：

1. `memory_ingest`「我喜欢喝咖啡。」→ 候选 `mem-5a3a2d9c…`
2. `memory_reject` → deleted
3. `memory_restore` → candidate
4. `memory_candidates` → 又出现，body「我喜欢喝咖啡」
5. `memory_tick` → `{"stale": 0, "ingest": {...}}`
6. 再次 `memory_reject` 清理测试数据

## 限制

- `stale` 只报告数量，没有列出具体记忆；需要时用 `memory_decay(dry_run=true)` 看明细。
- 恢复统一回到 candidate，不能直接恢复成 active。
- 衰减归档仍没有定时执行，是刻意保守。
