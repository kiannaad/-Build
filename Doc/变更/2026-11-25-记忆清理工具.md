# 2026-11-25 记忆清理工具

## 时间

2026-11-26 01:15–01:30（Asia/Shanghai）

## 原因

`deleted` 是软删除，测试与误删数据会一直占库；需要一个受控的物理清理入口，且不能一键误删。

## 改动

1. `db.purge_deleted(older_than_days=30)`：
   - 只选 `status='deleted'` 且 `updated_at` 早于保留期的行；
   - 删除记忆行，`memory_sources` / `memory_embeddings` 由外键级联清理，FTS 触发器同步；
   - 写 `purge_deleted` 审计（数量、id 列表、保留天数）。
2. MCP 新增 `memory_purge`：
   - `confirm` 必须为 `true`，否则直接报错；
   - `older_than_days` 默认 30，可设 0 清理全部 deleted。
3. 测试：未确认拒绝、确认后清除、重复清理为 0。

## 影响面

- 工具变为 20 个。
- 物理删除不可恢复；`confirm` 闸与保留期是仅有的两道保护。
- 只动 deleted，不动 active/candidate/core/events。

## 验证证据

```text
Ran 49 tests in 4.487s
OK
```

真实库：

- 清理前：`{"events":5,"memories":{"deleted":4},"core":{"confirmed":1},"audit":15}`
- `memory_purge(confirm=true, older_than_days=0)` → `{"purged":4, "ids":[...]}`
- 清理后：`{"events":5,"memories":{},"core":{"confirmed":1},"audit":16}`

## 限制

- 事件（L3）不会被清理；当前保留 5 条测试事件。
- 没有自动清理定时器；需要手动或后续接心跳（刻意保守）。
- 清理后 audit 里仍保留 id 列表，便于追溯。

## 回滚

物理删除无法回滚；如需恢复，只能从清理前的备份 `Backups/*.zip` 还原。
